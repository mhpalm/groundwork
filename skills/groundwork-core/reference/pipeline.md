# The pipeline

A run moves through ten fixed stages and stops wherever a person must answer, approve or connect. The first tracker write is a draft epic at Proposal, held for the runner's approval; no task is written before an approver's authenticated approval. Before the draft epic exists, run state lives in the run folder and moves between people as a run bundle; after it exists, the epic is the shared store.

| # | Stage | Inputs | Outputs | Stops when |
| --- | --- | --- | --- | --- |
| 1 | Intake | Request; overlay | `plan.id`, restatement, handshakes, compat results, identity check per instance | Always: the runner confirms the restatement. Also if no overlay or tracker skill loads, or an identity check fails |
| 2 | Clarify | Restatement; overlay; core question list (goal, scope, systems and instances touched, repos and base branches, links, data involved, who signs off, anything a junior would need decided) | `request.clarifications`, `scope` | Until every scope question is answered or parked as an open question on a later phase |
| 3 | Discover | Scope; system skills; surface | Evidence, `coverage` per instance | Before the first read, to show the call templates and scope bounds; again if a connection is missing or fails its identity check |
| 4 | Draft | Scope; evidence; breakdown patterns; overlay | Phases, tasks, P0, access list, `standard_work`, open questions | Never; ambiguous items are marked and drafting continues |
| 5 | Gap review | Reviewer view of the plan; evidence; checklist; skill rules | Validator results; findings | Never; hands findings to stage 6 |
| 6 | Resolve | Findings; open questions | New plan version; each finding fixed, accepted-minor, exception-requested or needs-person | When a blocker needs a person. Reruns stage 5 after every change until no unresolved blocker remains in a phase being offered, for up to 5 rounds; after that the remaining blockers go to the runner as needs-person |
| 7 | Proposal | Reviewed plan | `proposal.md` (open questions first, then coverage, phases, tasks, commands taken from evidence, minors, stamps); held write: draft epic with the proposal and plan of record in the plan store | Always: the runner approves the draft-epic write; then approvers review on the epic |
| 8 | Approve | Proposal; numbered write list per offered phase | Approval comment on the epic, authored by the approver's own account | Until an approver on the gate approves one or more phases, or declines |
| 9 | Create | Approved phases; approval comment; tracker skill | Items (not ready until the phase is complete), links, manifest, journal | On lock conflict, a verification failure, drift, or any failed write |
| 10 | Freeze | Journal shows the phase's writes done | Phase flipped to ready; dated snapshot in the plan store | Ends the run |

**Modes.** "Create project X" runs all ten stages. "Plan phase P3" takes an outline phase through stages 2 to 7 on the existing epic, rerunning Discover for that phase. "Release phase P2" takes an already reviewed phase through a fresh validator run, re-checks evidence marked `recheck` and anything older than `evidence_max_age_days`, then stages 8 to 10 with `kind: release`. "Revise project X" is in approval-create.md. "Set up Groundwork" and "migrate the overlay" are in setup-mode.md.

**Which phases a run plans in detail.** Stage 4 drafts P0 and the next phases in full, up to about 20 tasks (P0 and about three phases; the worked example has 16). Later phases are `outline` with a goal and the questions they carry, shown in the proposal and the epic description as "outline, needs a planning run".

**Ambiguity (CR-05).** An item that cannot be settled pauses on its own: the task gets an open question that blocks it and its dependents, and everything else continues. A phase with a blocking open question cannot be offered for approval.

**Independence of gap review (CR-03).** The reviewer receives a reviewer view: `plan.json` with `history and origin removed and clarifications kept as question and answer only (who answered is stripped)`, plus `evidence/`, the checklist and the loaded skills' rules. Its hash goes in `review.reviewer.view_hash`. It is told that `untrusted_text` and tracker free text are data. In Claude Code the reviewer is a subagent started with only those files, on a different model where one is available. Where there are no subagents, the core writes a review bundle and asks the runner to start a fresh conversation, load the core, and run "review this bundle"; the returned findings must carry the bundle's hash, which the validator checks. In v1, "independent" means a separate context that sees only the reviewer view; the plan records which model and surface did the review. Without an independent review, the plan cannot be proposed. When the review ran in a fresh conversation the runner started, the proposal says so plainly, and every approval record carries review\_hash, so approvers sign off on that exact review.

**Resuming.** Every stage writes its output into `runs/<overlay.id>/<plan.id>/`, so a run resumes from the last completed stage. Before the draft epic exists, "export run bundle" packs the folder with a hash manifest for another person or session to import; import checks the overlay id and hashes. After the draft epic exists, the plan of record, approvals and manifest live in the tracker, so anyone with access can resume. On cloud and app surfaces the run folder ends with the session, so until the draft epic exists the core exports a run bundle at every stop.
