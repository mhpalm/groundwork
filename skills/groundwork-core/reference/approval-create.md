# Approval, create and freeze

Approval releases specific phases at a specific plan version, authenticated by the approvers' own tracker accounts, and create writes exactly those phases. Create is safe to rerun at any point: every item carries a stable key, a chained manifest in the plan store records what was written, preflight adopts or stops instead of guessing, and a phase only becomes visible as ready once every item in it is written.

## What is hashed

Hashes are SHA-256 over RFC 8785 canonical JSON, computed by `check_hashes.py`. The hashed subset is normative and listed below and defined by `scripts/gw_hash.py`:

- `phase_hash`: the phase's id, name, goal, order, `depends_on` and `task_ids`, plus every field of each of its tasks (role by `role_key`, evidence by id). It excludes phase `state`, plan `status` and `version`, `stamps`, `review`, `history`, `coverage`, `epic.tracker_ref` and approvals, so moving a phase through its states never changes it.
- `plan_hash`: every `phase_hash`, plus `scope`, `request.starting_point`, `epic.title`, `epic.summary`, `open_questions` and `access_list`.
- `proposal_hash`: the bytes of `proposal.md` as rendered from the plan by `render_proposal.py`; create re-renders and compares.
- `write_list_hash`: the numbered write list, which names every write including lock comments, plan store files, manifest updates and labels.

Evidence ids are derived from the subject (`ev-<platform>-<instance>-<8 hex of subject>`), so re-reading the same subject keeps its id and an approval survives a refresh that finds the same facts. Mutation tests confirm that a state change leaves `phase_hash` alone and any task edit changes it.

## The draft epic

At Proposal the core offers one held write: create the epic with the overlay's draft label (default `gw-draft`), the overlay id, version and hash, and the rendered proposal in its description. The plan store gets the plan of record and an evidence file holding every non-restricted evidence item. The draft epic holds no tasks, and everything on it is safe for its viewers under CR-11. The draft label is removed by a listed write at the first freeze.

## Plan store, lock and manifest

**Plan store.** Files are put through the tracker skill as `<plan.id>-plan-v<N>`, `<plan.id>-evidence-v<N>`, `<plan.id>-manifest-<seq>` and `<plan.id>-snapshot-<seq>-<YYYY-MM-DD>`. Groundwork never overwrites a file. Trackers may let people edit what is stored, so immutability is detected, not enforced: every approval and manifest records the hashes of the files it relies on, and a file that no longer matches stops the run.

**Lock.** Neither GitHub nor Jira offers an atomic claim, so the lock is a protocol. To claim, post a `gw-lock` comment on the epic with the runner's account id, run id and an expiry 30 minutes out; then list lock comments, and the earliest unexpired claim wins. A loser posts a release and stops. The holder renews by posting at least every 10 writes; a renew counts only while the claim is still live, so a run that stalled past its expiry can never take the lock back from a run that claimed after it, and its own later claim is ordered by that claim's time. Only the account that posted a claim can renew or release it, and posts a release when it stops for any reason, success or failure. The same account resuming the same run may take over its own lock. Lock comments are housekeeping writes on the write list. The lock is required for allocating a new plan version or manifest sequence (plan phase, release, revise), for create and for freeze.

**Manifest.** Each manifest file lists every written key with its tracker id, its plan-owned hash, its links and its not-ready state, plus `prev_hash` of the previous manifest. After a retire records its intent, every manifest also carries `status_file` (`{state: intent | recorded, n, hash, at, set_by}`) forward unchanged (revise-mode.md, "Retire"). The latest manifest is the highest sequence whose `prev_hash` chain is intact. Create writes a new manifest after every batch of at most 10 writes, so a crash loses at most one batch of bookkeeping, which preflight then adopts. A manifest is the record of what was done once, so `make_manifest` refuses, and `check_hashes.py manifest-chain ... --plan-id ID` refuses again at every read (a hand edit can recompute a file's own hash), one that names another plan, drops a retire's `status_file`, drops a key the previous manifest records, moves a key to another tracker id, clears `blocked_set` or `split_comment`, rewrites `blocked_changes` (append only, alternating from the first clear, each in a later plan version), or clears, changes the reason of, or moves back a recorded close. `make_manifest` also checks every manifest against `manifest.schema.json` before it is written.

## Phase-by-phase approval

1. The proposal offers phases with no unresolved blocker and no blocking open question. Outline phases and phases with open questions are shown but cannot be offered.
2. With the offer, the core posts the numbered write list for those phases.
3. Each approver posts one approval record (plan-format.md) as a comment on the epic from their own tracker account. In a Groundwork session, the core shows the approver the phases, the short forms of `plan_hash`, `proposal_hash`, `review_hash` and `write_list_hash`, and the full write list, and posts only after the approver confirms. Elsewhere it gives the exact text to paste. A record approves the whole offer: its `phases` must be every phase the write list offers, because the write list and the proposal are one unit. An approver who wants only some of the offered phases says so in words, and Groundwork proposes again with the smaller offer, which gets its own write list, proposal and records.
4. Every gate whose `applies_to` is `all_phases` must reach its own quorum for each phase: `min_approvers` records from distinct accounts with the same `plan_hash` and `phase_hashes`. Exceptions need their own record on the `exception` gate; a phase-release record cannot accept an exception.
5. The drafter may approve their own plan, and it is not flagged. The record names the approver's account.
6. If a write-capable tracker skill is `unverified` on the surface, the proposal and write list say so, and each record must carry `accept_unverified_writer: true` or create refuses.
7. Any later change to an approved phase changes its `phase_hash` and voids that phase's approvals. Create must start within `create_window_days` (overlay, default 3) of the last approval; after that, approvers post fresh records for the same hashes. An expired record is listed as information, never a problem, so fresh records for the same proposal reach quorum and a crashed create can be finished. The retire's own resume is not held to the window once its status intent is recorded: it already started writing under a valid approval. A retire that crashed before that point (during its closes) is resumed like any create, with fresh records once the window has passed.

## Plan-level approval

Some changes offer no phase: declining a change request, moving it to its own epic, retiring the plan, or recording later work as an outline phase. They use a plan-level set.

1. The write list comes from `render_proposal.py plan-write-list --kind decline|own_epic|later --entry ENTRY.json` (the change-request entry it decides, from `change_request.py bind LOG.json CR-n --outcome ... --reason ...`: the logged pending entry as allocated, restatement, source, origin and base included, with the outcome and reason filled in and no `decided_by`), or for a retire from `retire.py write-list` (revise-mode.md, "Retire"). It never creates, edits or releases an item. Each kind allows only its own writes (`check_hashes.PLAN_LEVEL_WRITES_BY_KIND`): decline, own epic and later write the lock, the change-request log entry and the snapshot, and no manifest, because they write nothing to the tracker (a later set's plan version is stored at Proposal, like every plan of record); only retire closes items, writes the status file, removes the draft label and closes the epic. A bound entry's outcome must match the kind (`declined`, `own_epic`, `later`). `check_hashes.py plan-level` rebuilds the write list from the plan of record, its kind and the stored context (for a retire, the closes follow from the items the proposal showed and the runner's leave-open choices) and refuses any other, including one for another plan or plan version.
2. The proposal is rendered (`render_proposal.py plan-level`) from the plan of record, that write list and a proposal context stored at Proposal (`render_proposal.py context`, saved as `proposal-context-<n>.json`), which lists the epic's items at that time and the pending sets it replaces. It shows everything the approvers bind: the change-request decision with its reason, the plan status change, every close, and for a retire every item left open with its owner, every person-added child and every pending phase set it voids. Write-list fields that are objects are printed in full, never dropped.
3. Each approver posts a record with `scope: plan_level`, `phases: []` and the kind. Every `all_phases` gate must reach `min_approvers` on plan-level records; zero records never pass; records must agree on the kind, and it must be the write list's kind; none can accept an exception; `create_window_days` applies. `check_hashes.py plan-level` verifies all of this.
4. A set that changes no version (decline, own epic, retire) is checked at create with the integrity profile (schema, hashes, GR-17, GR-34) and an independent review of a "closes and decisions" bundle: the items to close with their reasons, what is left open, the change-request entry and its assessment, and any status change. Build it with `check_hashes.py view PLAN.json --plan-level --write-list WL.json --context CTX.json [--assessment A.json] --rules ... --out BUNDLE.json` and give it to the reviewer in a fresh conversation. The records bind that review. `check_hashes.py plan-level` rebuilds the bundle itself from the stored context (`--context`), the stored assessment (`--assessment`), the rules (`--rules`) and its own checklist version, never from a bundle file, and refuses a set whose review was made from anything else, including the plan's ordinary Gap review. It also re-renders the proposal from the plan of record, the write list, the stored context and the stored assessment (which the proposal shows in full), and refuses if the proposal the approvers signed differs by a byte. Any blocker finding in the review that isn't `fixed` stops the set. Kind `later` stores a new plan version and binds a full Gap review. A change that alters plan content and offers a phase needs a phase set.
5. Before writing, create re-reads `list_children` and `find_by_key`, and `create_steps.py recheck` stops with "re-propose" if an open plan-owned item exists that the stored context didn't list (for example one another set created after this proposal).
6. The change-request entry is written with `change_request.py decide CR-n --plan-id ID --logs LOG_1.json ... --write-list WL.json --proposal PROPOSAL.md [--restricted RESTRICTED.json]` (the hash in `decided_by` is computed from the verified proposal file itself): the outcome and reason come from the entry the verified write list binds, never from values typed at create, and deciding again with the same set is a no-op, so a resume can finish. The change-request log and the status file have more than one possible writer. Their file number is allocated at write time under the lock, and a log write is the latest file plus this set's own entry, so a decline made at the same base is never dropped. The write list binds the entry, not the number.

## Create

**Lock**, then **verify** (read-only):

- Connect with the runner's own access; confirm the instance and project match the overlay, the epic's overlay id matches, and the runner's overlay hash matches the latest anchored overlay record (setup-mode.md) (CR-12).
- **Retire gate, first of all.** `check_hashes.py approvals` and `plan-level` refuse to run without `--latest-version` (the latest plan of record stored), `--manifest` (the latest manifest, or `-`), `--status` (the latest status file, or `-`) and `--epic open|closed`. They run `retire.py gate` before any record is read: a retired plan, a retire in progress or a closed epic refuses every set except the resume of the retire's own set. Every other operation that writes (resume, freeze, release, revise, plan phase, change request) runs `retire.py gate` itself before it takes the lock.
- **Grouping filter, first.** Only approval records whose `plan_version` equals the current version (the latest plan of record in the plan store) and whose `proposal_hash` equals the proposal being created count. This filter runs before any other per-record check. Records for earlier versions are listed as superseded, and records for another proposal at this version (a decline beside a pending release) as another set; neither ever stops create, and a malformed or edited record in another set can't fail this one. A record that can't be parsed far enough to read its version and proposal hash is listed as information. If a newer version is stored than the one this set approved, the set is void: storing a new version voids every pending set at older versions, phase and plan-level alike, and the runner re-proposes.
- For each approval comment, read through the API that its author's account id is on the gate in the anchored overlay and that the comment has never been edited (its updated time equals its created time). Recompute `plan_hash` and `phase_hashes` from the plan of record, `proposal_hash` by re-rendering from stored inputs only (the plan of record, the write list and the proposal context named by `plan_store_ref`, never session state or a fresh tracker read), and `write_list_hash`. The write list itself must be the one Groundwork renders from the plan of record for that offer, with the closes, edits and change-request entry it names (`check_hashes.py approvals` rebuilds it and compares hashes), so a hand-added write such as an epic close is refused even when every record binds it. The review the records bind must be the review recorded in the plan of record, with no open blocker. Every write in the list carries `scope: phase:<id>` or `scope: plan`; a phase set authorizes its own phases' writes and the plan writes in the same list (closes the revise diff removes, the change-request log entry), and nothing scoped to a phase it doesn't approve. Rerun `validate_plan.py`. Any mismatch stops create.
- Re-read evidence marked `recheck`. If a fact changed, stop; the phase goes back through Draft and Gap review as a new plan version.

**Preflight** (read-only). `--phases` must be exactly the verified write list's offer, or preflight refuses. Every found item carries its status from `create_steps.py status`; an item without one stops, because the finished-work and closed-not-done rules read it. A task whose dependency is neither written nor in this offer stops, because its dependency link could not be made: write that phase first, or offer it with this one. `find_by_key` searches the key slot across the whole tracker project, not only the epic's children; `list_children` cross-checks. Items in the phases being written:

| Found | Latest manifest says | Action |
| --- | --- | --- |
| No item with this key | Never written | Create |
| Item with this key | Written, same plan-owned hash | Skip |
| Item with this key | Never written | Adopt if its plan-owned hash matches the planned item (the crash-before-manifest case); otherwise stop as drift |
| Item with this key, not under the epic | Any | Adopt and add the missing parent link as the next write |
| Item with this key | Written, same hash as the manifest, but the plan's text differs | Update, only when the verified write list has an `update_item` write for this key whose `owned_hash` equals the rendered text's hash, and only while the item is not done or closed not done; otherwise stop, so an approved edit is never skipped, nothing else is ever written, and finished work is never edited |
| Item with this key | Written, different plan-owned hash | Stop: drift. The one exception: the write list updates this key and the tracker already holds exactly the planned text (an update written before the session ended), which is adopted |
| No item with this key | Written | Stop: drift, deleted or moved; never recreate silently |
| Item with this key, larger points | Any | Keep the points; post one comment recommending a split, under the write list's `comment_split` entry, recorded as `split_comment` so it is never repeated |

Items in other phases are compared too, but differences there are reported as warnings, not stops, so a person adding notes to an earlier task doesn't block a release.

**Plan-owned hash.** Covers the title, the sections of the body Groundwork wrote, the role key, the phase and the key. Each tracker skill provides a `normalize` procedure that reads those fields back into the same form they were written in (Jira ADF and GitHub Markdown differ), with mutation tests. The hash is kept in the manifest, not in the item, so no extra field is needed. Status, checklist ticks, assignee, comments, people's labels and points are excluded. Links are checked against the manifest separately.

**Writes.** Tasks in phase and dependency order, each created with its key and the not-ready marker in the same call; parent links and dependency links next; then `set_blocked` on every task with a `waits_on`, recorded in the manifest as `blocked_set` so it is applied once and never again after a person clears it; a new manifest after every batch. Each `create_item` write binds the `owned_hash` of the text it creates, and preflight stops on a PLANNED item the write list doesn't create with exactly that hash, or a create it leaves out. A revise that removes a wait writes `clear_blocked`; once it lands, the manifest item records `{state: cleared, plan_version}` in `blocked_changes` (`create_steps.blocked_record`). A wait added back later changes the task's body, so its phase is offered and its `set_blocked` write applies again, recorded as `{state: set, plan_version}`. `create_steps.py done` checks both. Every link, unlink and blocked write reads the item on the tracker first: a write that landed before the session ended is recorded in the manifest, never made twice. On partial failure, create stops, writes the manifest, releases the lock, and the phase stays not-ready. "Resume create" reruns lock, verify and preflight; preflight's adopt rule covers anything written after the last manifest. Created items are never deleted automatically; abandoning a phase means a held write that closes its items.

**Close.** Groundwork closes an item only through the close procedure, from the approved write list, with a reason (`not_planned`, `superseded`, `duplicate`, `completed`). `create_steps.py close` orders the steps: first a manifest recording the close intent, as a batch of its own; then, per item, the `gw-closed:<reason>` label and the tracker's close; then a manifest recording each close as done. An item already closed is skipped and never relabelled, but its outcome is always recorded, so the completion check can finish: a close whose `gw-closed` label is on the item (Groundwork's own transition that landed before a crash) is recorded as `closed`, and an item a person finished first is recorded as `finished`, which reads by the tracker's own status from then on. `create_steps.py close WL.json RAW.json --overlay OVERLAY.yaml --plan-id ID --manifests ...` reads the statuses from the tracker's raw reads itself; set each manifest item's close to the `records` of the `manifest_closed` step. If the tracker needs a person for the close (Jira: no direct transition, a required screen field, or more than one hop), stop and name the item; it stays close pending and is retried on resume.

**Reading item state.** `create_steps.py status` turns each item's raw state into `todo`, `in_progress`, `done` or `closed_not_done`. A `gw-closed:` label counts only when the manifest recorded that close, so a person adding or removing the label changes nothing; an open item with a recorded intent is close pending; a reopened item that Groundwork closed is drift. Any other close reads by the tracker's own status, resolution or reason against `field_map.statuses.closed_not_done`. A task that depends on a `closed_not_done` task stops create until a revise re-points the dependency.

## Freeze

With every task and link written, the phase moves to `writing` and the not-ready markers are cleared item by item, each recorded in the manifest, so an interrupted flip resumes where it stopped. When the manifest shows every item ready, the phase becomes `released`, the snapshot is stored, the first freeze also removes the draft label from the epic, and the lock is released. Where the tracker supports it, the not-ready marker is a workflow state as well as a label, so a person removing the label alone doesn't make an item look ready; release mode reports any item found ready early. The epic description lists unreleased phases as "planned, not released" or "outline, needs a planning run". `plan.status` is `active` while any phase is not `released` and `complete` when all are.

## Formats on the tracker

- **Approval comment.** A comment whose body contains the approval record as a fenced block that starts with three backticks and `json`. Any other text in the comment is ignored. `check_hashes.py approvals` reads every epic comment, keeps only records for this plan id, and refuses any comment whose updated time differs from its created time.
- **Lock comment.** One line: `gw-lock claim|renew|release run=<run id> account=<account id> expires=<UTC time>` (no `expires` on release). `create_steps.py lock` decides the holder. A lock line counts only when its account matches the comment's author.
- **Owned section.** Every item body Groundwork writes keeps the plan-owned text between `<!-- groundwork:owned:start -->` and `<!-- groundwork:owned:end -->`. People may add anything outside the markers; it is never drift.
- **Plan store names.** `<plan.id>-plan-v<N>`, `<plan.id>-evidence-v<N>`, `<plan.id>-manifest-<seq>`, `<plan.id>-snapshot-<seq>-<YYYY-MM-DD>`, never overwritten.

## The create procedure, step by step

1. `create_steps.py lock` with the epic's lock comments. If it says `claim`, post the line it gives, read the comments again and repeat. Continue only on `held`. On `lost`, post the release it gives if you posted a claim, and stop.
2. Read the latest anchored overlay record from the anchor issue, the epic's comments, the plan of record, the proposal, the write list and the review, plus the latest stored plan version, every manifest file in the plan store (`--manifests`; the latest is derived from the chain, never named), the latest status file and the epic's state. Run `check_hashes.py approvals` with all of them, plus `--evidence` and `--rules`: it re-renders the proposal from the plan of record and the write list and refuses one that differs, and it rebuilds the reviewer view and refuses a review made from any other. Any problem stops create.
3. Run `validate_plan.py --stage create --offer <approved phases> --now <now>`. Re-read every evidence item marked `recheck`; if a fact changed, stop and send the phase back through Draft and Gap review.
4. For each planned item, and each key the write list closes, render its body with `render_proposal.py task` where it is planned, compute its plan-owned hash, then `find_by_key` across the tracker project and `list_children` on the epic; read each found item's status with `create_steps.py status`. Read each found item back through the tracker skill's `normalize` and hash it with `check_hashes.py owned`. Run `create_steps.py preflight PLANNED.json FOUND.json --phases <the offer> --write-list WL.json --plan-id ID --manifests ...` (with `--relies-on` on a revise apply's first preflight).
5. Write the change-request decision first when the write list binds one (`change_request.py decide`), so a crash leaves it decided by this set. Then carry out the preflight actions in order: create (key and not-ready marker in the same call), adopt, update (the tracker skill's "update owned fields", replacing only the owned section), adopt_update, skip, add missing parent links, then dependency links; then the write list's plan-scoped `unlink_dependency`, `link_dependency` and `clear_blocked` writes for written tasks a revise re-pointed or unblocked (each skipped when the manifest's links already show it); then `set_blocked`; then the close procedure for each `close_item` (`create_steps.py close WL.json RAW.json --overlay OVERLAY.yaml ...`); then clear the not-ready markers and write the snapshot. Write a manifest with `create_steps.py manifest` after every 10 writes and at the end, and record each link change in the manifest item's `links`. Post one split-recommendation comment for each `comment_split`.
6. Renew the lock at least every 10 writes, and after each renew run `create_steps.py lock` again: on anything but `held`, stop at once without a release (the lock is no longer yours; a renew after expiry never counts). On any failed write: write the manifest, release the lock, report which write failed. "Resume create" starts again at step 1.
7. Before the lock release, run `create_steps.py done WL.json --plan-id ID --manifests ... [--logs ...]`. It lists every approved write the manifest or the change-request log does not show as done; if it lists anything, stop and resume rather than release as finished.
