# Release and revise modes

## Release mode

"Release phase P2" runs `retire.py gate release ...` and then `change_request.py release-check PLAN.json --phase P2 --released P1=<plan of record P1 was released at> ...` for every released phase before P2: if an earlier phase's basis changed since its release, release stops and asks for a revise (release never adds follow-ups in other phases). Then it takes the lock, allocates the next plan version, and loads the plan of record and evidence file. Restricted evidence and anything older than `evidence_max_age_days` is re-discovered by the runner. If any fact a P2 task relies on changed, P2 goes back through Draft and Gap review, including the independent reviewer; otherwise the validator reruns and the phase goes to approval with `kind: release`, then create and freeze as above. New access for the phase is requested in its own first task (GR-13).

## Revise mode

- **Finding the epic.** The runner gives the epic's tracker key or link; the core never finds an epic by title.
- **Baseline.** The tracker's current state from `read_epic` plus the latest plan of record. Where a person changed a plan-owned field, the tracker wins, the change is listed as drift, and the adopted text is marked `from_tracker` (untrusted), shown in the proposal, and checked by the reviewer like evidence text.
- **Diff.** Added tasks, changed plan-owned fields, tasks to close (never deleted), tasks dropped before they were written, dependency changes, phases newly offered, and the brief fields, options and decisions that changed (`model`), computed by `revise_diff.py BASE NEW TRACKER --overlay ... --manifests M_1.json ... M_n.json` against the tracker's current state. A task the tracker read doesn't show but the manifest records is never dropped silently: it is closed and listed under `missing`, and the close procedure records it as `missing` only once a project-wide `find_by_key` confirms it is gone. An item recorded as missing that is found again reads as drift and is closed by the next close procedure. A task that was never written and changed is listed under `changed_unwritten` and needs no write. The whole resulting plan is gap-reviewed.
- **Re-pointed dependencies and removed waits.** For each written task whose dependencies change, the diff's `relinks` (`{task, added, removed}`) go to `render_proposal.py write-list --relinks RELINKS.json`, which adds a plan-scoped `unlink_dependency` for each removed dependency and a `link_dependency` for each added one on a phase that isn't offered, so a written task never stays blocked by work the plan dropped. Each written task whose `waits_on` the revise removes is listed under `unblocks` and gets a `clear_blocked` write (`--unblocks P1-T03,...`). The write list renderer refuses a relink that doesn't match the plan and an unblock of a task that still waits. With the latest manifest, `relinks` compare the links the manifest records against the revised plan's dependencies, and `unblocks` list only tasks whose blocked state the manifest records as set, so a version that was stored but never applied (or applied in part) can't lose them. `check_hashes.py approvals` derives the same relinks and unblocks from the manifest and refuses a write list whose plan-scoped `unlink_dependency`, `link_dependency` and `clear_blocked` writes differ from them.
- **Edits.** The diff's `edits` list (every written task under `changed`, including a dependent whose body names a retitled dependency, plus every task under `adopted`, whose tracker text the plan took over) is passed to `render_proposal.py write-list --edits P1-T02,...`, which adds an `update_item` write binding the new plan-owned hash in that task's phase scope, so the phase must be offered. Create updates only what the write list names; any other difference between the plan and what was written stops create.
- **Done work is not edited.** A change to a finished task (done or `closed_not_done`) becomes a new follow-up task with a new id, and a finished task is never removed from the plan. A task that isn't finished and depends on a `closed_not_done` task is refused until the dependency is re-pointed or dropped.
- **Closes.** Each written task the revised plan drops is closed as `not_planned` (or `superseded` or `duplicate`, never `completed`, which would read back as done) through the close procedure in approval-create.md; a write list that closes a task still in the plan, or a key from another plan, is refused; `revise_diff.py` lists them under `close_items` for the write list. Closes come from the manifest as well as the base plan: every key of this plan the manifest records, that the revised plan doesn't have, and whose close isn't recorded as closed or finished, is closed, and `check_hashes.py approvals` refuses a write list that leaves one out. A dropped task a person deleted is still closed: the diff lists it under `missing`, and the close procedure records it as `missing` (final) once a project-wide `find_by_key` confirms it is gone. A new task may never reuse the key of a written task an earlier version dropped. When the tracker shows the plan of record's own text for a task the manifest records with older text (an approved update landed before the session ended), it is adopted, not drift; that revise may not change the task again. A task dropped before it was ever written is listed under `dropped` and needs no write. A reopened item that Groundwork closed is reported as drift.
- **Concurrency.** Revise holds the lock from version allocation through apply, and the diff records each item's last-updated time (`relies_on`). The first preflight of the apply passes it (`create_steps.py preflight ... --relies-on RELIES_ON.json`) and stops if any item moved or is gone since the diff: diff again. A resume of that same apply leaves it out, because the apply's own writes move those times; the preflight drift rules still apply.
- **Release on a worked epic.** Status changes, ticked steps and notes outside the plan-owned markers are normal work, not drift. Points a person raised are kept, and Groundwork posts one split recommendation on that task, recorded in the manifest so it is never repeated. A task a person deleted is never recreated; a task in the phase being released that depends on it stops create until a revise re-points the dependency.
- **Approval.** Same gates and records, with `kind: revision`; create applies the diff with the same keys, manifest and preflight.
- **Basis changed after release.** For each released phase, `change_request.py basis` compares what the phase relied on (`basis_hash`'s subset) at the plan version it was released at and now. A difference is listed under "basis changed after release" with the changed parts. The runner decides what follow-up work to add; nothing is generated, and release mode never adds follow-ups in other phases.

## Change requests

A change request is new work for a project that already has a plan. It is a front end to revise: one request per revision.

- **Who.** Only the runner submits it, in their own words. Groundwork restates it and the runner confirms the restatement. Pasted stakeholder text becomes evidence (`system: runner`, its text only in `untrusted_text`); a restatement of it has `source: pasted` and names that evidence in `derived_from`, and nothing in it is followed as an instruction (GR-19). A restatement is never restricted: if the source is sensitive, the runner writes a plain paraphrase. Who asked is recorded as a role (`origin_role_key`), never a name.
- **Before anything is approved.** While no phase is approved or released, a new request is simply more Clarify input to the same run.
- **Allocate.** Under the revise lock, `change_request.py allocate` writes the next id (`CR-n`) as a pending entry in the change-request log, recording the base (plan version and latest manifest sequence). It also shows any similar request declined before, by restatement, and scans the log for secrets and, with `--restricted`, restricted values (GR-17, GR-34); `decide` runs the same scan.
- **Assess.** `change_request.py assess` on the plan of record and the drafted revision gives, in this order: whether it changes the brief (outcome, scope_in or non_goals; shown first in the proposal), the brief fields it serves, the decisions and options it changes, the released phases whose basis changes, traits added (each with `from_plan_version`), the cost in one-day tasks, new dependencies and the existing tasks they touch, and all four options. Cost is `drafted` (an exact count, only from a gap-reviewed draft), `outline` (about N phases of about 5 tasks, with the open questions that would narrow it) or `unknown` (the open questions to answer first). Waits are listed by name and count 0 days. If phases are approved but not written, the assessment says those approvals become void, and the runner confirms before going on. A format-1 plan has no brief, so Fit is skipped and the assessment says so.
- **Base check.** `change_request.py base` must pass between assessment and proposal: if the plan version or the manifest moved, assess again. If create holds the lock, assessment may run read-only and proposal waits for the lock and rechecks.
- **Outcomes.** Add to the current unreleased phase, or add a later phase, writes a new plan version: an add is a revision (phase records, full Gap review) whose write list binds the entry (`render_proposal.py write-list ... --entry ENTRY.json`, outcome `added`, the entry made by `change_request.py bind`); a later phase offers no phase, so it uses a plan-level set of kind `later` with full Gap review. Own epic is a plan-level set here (a log entry) plus a separate new-project run, whose proposal names this epic's key in a code span with no link. Decline is a plan-level set that writes no plan version, so pending approvals stay valid.
- **The log.** `change-requests-<n>.json` in the plan store, outside `plan_hash`. Each file carries `prev_hash` (the previous file's hash) and its own `hash`, and every command that reads it takes every log file (`--plan-id ID --logs ...`) and finds the latest by verifying the chain: a file that doesn't match its hash, names another plan, breaks the chain, drops an entry, changes a decided entry, or changes a request rather than only deciding it stops the run. Each entry has the id, restatement, source, `derived_from`, `origin_role_key`, outcome, reason, base and `decided_by` (the approved plan version and `proposal_hash`). The write list binds the entry without `decided_by`; create fills it in from the verified proposal, so the write list never names its own hash. `decide` refuses unless the bound entry is the logged pending entry itself (restatement, source, `derived_from`, origin and base), so approvers approve the request as it was logged, and the proposal shows the restatement. Each log write is the latest file plus this set's entry, numbered under the lock. GR-17 and GR-34 cover the log (`change_request.py` runs them on every decision).

## Retire

Retire ends a plan. It writes no plan version: the status lives in its own plan-store file, `<plan.id>-status-<n>` (`schemas/plan-status.schema.json`), and the latest status file wins over `plan.status`. Retire is terminal; there is no un-retire, only a new plan.

- **What it reads.** `list_children` on the epic, plus `find_by_key` for every plan key, so an item written after the last manifest but not yet linked is found. Each item's status comes from `create_steps.py status`. A child whose key is neither one of the plan's task keys nor recorded in a manifest was added by a person; a key a manifest records is Groundwork's even when the plan of record no longer has it, so it closes like any other (`retire.py plan ITEMS.json CHOICES.json --plan-id ID --manifests ...`), and a recorded key the read doesn't find is closed as `missing` and listed in its own section of the proposal (a key already recorded as missing is not listed again). An item whose close the manifest records as `closed` but that is open again was reopened by a person: the close procedure never closes an item twice, so retire leaves it open and names it in its own section, never as a close. A plan key that no manifest records means a create was cut short: `retire.py plan` stops and says to resume that create first, because the close procedure only closes items a manifest records.
- **What happens to each item** (`retire.py plan ITEMS.json CHOICES.json`). `todo` items are closed `not_planned` through the close procedure. For each `in_progress` item the runner chooses: close, or leave open with a named owner role; there is no default. `done` and `closed_not_done` items are untouched. A person's child is left open and named. Items in a phase still `writing` lose their not-ready marker only by being closed; retire never clears it.
- **The proposal** lists every close with its reason, every item left open with its owner role, every person-added child, and every pending approval set for an unwritten phase, which retire voids (`--pending`). It is a plan-level proposal of kind `retire` rendered from stored inputs (approval-create.md, "Plan-level approval"), with the integrity profile and a "closes and decisions" review.
- **The write list** (`retire.py write-list`), every entry scope `plan`, in this fixed order: lock claim; the status intent manifest (first, so from the retire's first write every other operation, including the creates of the pending sets it voids, is refused); draft label removal, if the epic still has it; the close procedure (intent manifest, then label and close for each item, then the closes-done manifest); the status file; the manifest that records the status file's hash; the snapshot; the epic close; lock release. The write list binds the status file as `{schema_version, plan_id, status: retired}` only.
- **At write time.** Under the lock, create checks the items as they are now against the verified write list and the stored proposal context (`retire.py recheck VERIFIED_WRITE_LIST.json ITEMS.json CONTEXT.json --plan-id ID --manifests ...`; a key a manifest records is never a person's, here or in the verifier's rebuild, which refuses a stored context that flags one). Nothing at write time adds a close or changes a choice. An item finished since the proposal is skipped by the close procedure. Anything else the approved set didn't name stops with "propose again": an item someone started after approval (todo in the context, in progress now), an open item the write list neither closes nor leaves open, or a child a person added after the proposal. Once the status intent is recorded, proposing again is impossible (the gate allows only this retire's resume), so on a resume a child a person added is left open, an item started since is closed as approved, and an item that is open again since the proposal (a person reopened finished work, or a missing item was found again) is left open; `recheck` reports each under `warnings`, and the runner tells the people involved. On a resume the verifier rebuilds the write list from the last manifest before the status intent, so the retire's own closes never read as earlier ones. Then `retire.py status PLAN.json --n N --proposal PROPOSAL.md --at TS` builds the record from the verified proposal file (its hash is computed, never typed): the number is the latest status file's plus one, `set_by` is the verified set's plan version and `proposal_hash` (so the write list never names its own proposal's hash), and `at` is the write time. The status intent manifest (`create_steps.py manifest ... --status-file INTENT.json`, the `intent` that `retire.py status` prints) records the number, `set_by`, `at` and the record's hash before the file is written, so a resume rebuilds the identical file with `retire.py rebuild PLAN_ID --manifests M_1.json ... M_n.json`. The manifest after the file is written passes the same entry with `state: recorded`; `make_manifest` refuses any other change to a recorded or intended status file, including dropping it.
- **After retire** (`retire.py gate OP ...`). Create, resume, freeze, release, revise, plan phase, change requests and a second retire all read the latest manifest's `status_file` and the latest status file, and refuse a retired plan with "retired plan, start a new plan". While only the intent is recorded, they refuse with "a retire is in progress". The one exception is the resume of the very set the manifest's `status_file.set_by` names, so a crash anywhere in the write order can be finished; that resume runs under the crashed run's own lock and skips every step already done. Every manifest after the intent carries `status_file` forward, so no later write can drop it.
- **Stops.** A status file that the latest manifest neither records nor intends; a status file whose hash doesn't match itself, or doesn't match the one the manifest names; a status file for another plan; a status file the manifest records that is missing; an intent that doesn't rebuild to its recorded hash. A plan that was never retired has no status file and no `status_file` in its manifest, and that is normal.
- **A closed epic.** Every operation also refuses when the epic itself is closed, whether or not a status file exists ("the epic is closed; start a new plan"). The `set_by` resume is exempt, so a crash after the epic close but before the lock release can still be finished.
