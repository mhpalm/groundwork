# Correctness rules (GitHub)

These add to the core's gap-review checklist (they can only make review stricter). `rules.json` is the copy scripts read; this table mirrors it.

| Id | Applies when | Check | Severity | Source |
| --- | --- | --- | --- | --- |
| `github.pr-review-before-merge` | A task merges into a branch whose protection or ruleset requires approving reviews | The merge is a dependency of the next task with the reviewer's review in waits_on; no task merges its own pull request without the required approvals | blocker | [docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) |
| `github.required-checks` | The target branch requires status checks | A code task's verify step names the required check and its done state is that check green | blocker | [docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) |
| `github.no-self-approval` | A task needs a pull request approved | The approving reviewer is a different role holder from the pull request's author; a plan never relies on the author approving their own pull request | blocker | [docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews) |
| `github.code-owner-review` | The branch requires review from code owners and CODEOWNERS covers the changed paths | The review wait names the code owner role from CODEOWNERS evidence | blocker | [docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) |
| `github.environment-approval-wait` | A deploy job references an environment with required reviewers | The task after the deploy has a waits_on of kind approval owned by the reviewer's role; a rollback redeploy to the same environment needs its own approval wait | blocker | [docs](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment) |
| `github.dispatch-on-default-branch` | A rollback or redeploy relies on workflow_dispatch | Evidence shows the workflow with workflow_dispatch exists on the default branch | blocker | [docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows) |
| `github.secrets-not-readable` | A step needs a secret value | No step reads, prints or copies a secret value; steps that need one name the secret and say who sets it | blocker | [docs](https://docs.github.com/en/rest/actions/secrets) |
| `github.rules-layer` | Both branch protection and rulesets exist on a branch | Instructions account for every applicable rule from both sources | minor | [docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets) |
| `github.tested-commit-released` | A task tags or deploys a release | The task compares the commit tested on staging with the commit it releases and blocks on any difference other than planned release-notes changes | blocker | [docs](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment) |

Sources read 2026-11-14. Two points rest on partial reads and are rechecked before release: the exact `workflow_dispatch` default-branch sentence, and the repository-level wording that secret values are never revealed (the organization endpoints say so verbatim).
