# Changelog

## Unreleased

- Fixed (fifth review): a revise now removes the tracker link of a dependency it re-points (`unlink_dependency`) and clears the blocked state of a task whose wait it removes (`clear_blocked`), from the diff's new `relinks` and `unblocks` through `write-list --relinks/--unblocks`; both tracker skills gain the call. A retire writes its status intent first, so the pending sets it voids can't be created even after a crash mid-close. A revision's change-request decision is its first write. The first preflight of a revise that closes a task no longer stops on its own `relies_on` (FOUND holds the keys it closes). `create_steps.py close` takes the verified write list, not a free list, and the close procedure never closes as `completed`. Every command that reads the manifest (`preflight`, `manifest`, `status`, `close`, `done`, `approvals`, `plan-level`, `retire.py gate` and `rebuild`, `revise_diff.py`) takes `--manifests` (every file) and derives the latest from the chain. Create re-reads the lock after each renew and stops unless it still holds it. A new `create_steps.py done` lists every approved write the manifest or the change-request log doesn't show as done, before the lock release. A set that decides a change request is verified only with that request's stored assessment.

- Fixed (fourth review): a renew posted after a lock claim expired no longer revives it, so a stalled run can't take the lock back from the run that claimed after it, and a run's later claim counts from its own time. Preflight stops when a task depends on one that is neither written nor in the offer (its dependency link was silently lost), when a found item has no status, and, in the CLI, when `--phases` is not the verified write list's offer. `check_hashes.py manifest-chain` takes `--plan-id` and applies every append-only rule at read time, so a hand-edited manifest with a recomputed hash is refused. The change-request log is a hash chain (`prev_hash`, `hash`), read only through `--plan-id ID --logs ...`, and refuses dropped, reopened or rewritten entries and another plan's log; `decide` hashes the proposal file itself (`--proposal`). Revise closes are limited to tasks the plan drops, from this plan, never as `completed`. Plan-level write lists are rebuilt at verify (a retire's closes from the stored items and leave-open choices) and must name this plan and version. Decline, own epic and later may no longer write a manifest. Phase write lists name the split-comment procedure, so the approval covers it.

- Fixed (third review): a phase set is verified against the write list Groundwork renders from the plan of record, so a write added by hand (an epic close, for one) is refused even when every record binds it; the records must bind the review the plan of record carries, with no open blocker; the reviewer view leaves out the epic key, plan status, phase states and evidence bookkeeping (`collected_at`, record hash), so setting them after review no longer voids approvals; both write-list commands print `write_list_hash`; the phase proposal names every update, close and change-request decision. A change-request decision binds the logged request itself (`change_request.py bind`), and `decide` refuses one whose restatement, source, origin or base differ. A manifest can no longer drop an item, move it to another tracker id, or forget a close, a blocked flag or a split comment. The first preflight of a revise apply rechecks every item's last-updated time (`--relies-on`). Plan-level proposals show the stored assessment and are verified with it. Docs: a record approves the whole offer, `body_owned` includes both markers, plan-level sets write no manifest, and the `check_hashes.py` usage names every required flag.

- Fixed (second review): approvals now re-render the proposal from stored inputs and refuse one that differs, so approvers can't be shown one decision while the write list binds another; plan-level sets rebuild their review bundle from the stored context, assessment and rules, and an open review blocker stops them; a phase set's review must be of the plan's own reviewer view. An expired approval record is information, so fresh records can finish a crashed create, and the retire's own resume isn't held to the window. An update writes only the text the write list binds and never edits finished work. Revise edits only written tasks, records adopted tracker text through an update instead of stopping on it for good, and never drops a task the manifest records (`--manifest` required). A revision can bind an `added` change-request entry (`write-list --entry`). The retire recheck reads the verified write list and the stored context, never choices typed at write time.

- Fixed (review of the planning-model builds): `check_hashes.py approvals` and `plan-level` now require the latest stored version, the latest manifest, the latest status file and the epic's state, and run the retire gate first, so a pending phase set can no longer be created on a retired plan or closed epic. Revise no longer writes close entries for tasks that were never written (they are `dropped`), which could stop create halfway. Approved edits to written tasks are now written: the write list carries `update_item` writes (`--edits`), and preflight updates only what the write list names and stops on any other difference. Plan-level proposals show the change-request decision, the status change, items left open, person-added children and voided sets, and print every write field. Create decides a change request from the entry the verified write list binds, and a resume of the same decision is a no-op. Each plan-level kind allows only its own writes, and a record's kind must be the write list's kind. A decline, own epic or retire binds a review of its own closes-and-decisions bundle (`check_hashes.py view --plan-level`). Every retire and plan-level step now has a script (`create_steps.py manifest --status-file`, `retire.py rebuild|recheck`, `render_proposal.py plan-write-list|context`). Release stops when an earlier released phase's basis changed (`change_request.py release-check`); `revise_diff.py` lists brief, option and decision changes; an `elapsed` wait must state its condition (GR-16); the change-request log is scanned for restricted values (`--restricted`) at allocate and decide. The G6 golden no longer expects a close for an unwritten task.

- Added (planning model build 6): retire. `retire.py` decides what happens to each item (todo closes `not_planned`, in-progress follows the runner's close or leave-open choice, person-added children stay open and are named, a plan item no manifest records stops until its create resumes), builds the plan-level write list in a fixed order (draft label, closes, status intent, status file, the manifest recording its hash, snapshot, epic close, lock release), and re-derives the retire at write time so work started after approval stops it. The status lives in a new `status-<n>.json` (`schemas/plan-status.schema.json`) named by a new manifest field `status_file`, carried forward by every later manifest. `retire.py gate` makes every later operation refuse a retired plan, a retire in progress or a closed epic, except the resume of the retire's own set, which finishes a crash at any point.

- Added (planning model build 5): assess and adopt by reference. `assess.py` reads one bounded scope (at most 200 items), keeps structure (`legacy-refs.json`) apart from ticket text (`working-text.json`, restricted, never written to a plan store, proposal or tracker), turns v1 rule failures into recommendations the runner accepts one at a time, writes a report for the runner only, and checks that no working text was copied into anything Groundwork writes. Adopt starts a new plan with `legacy_refs` (in `plan_hash`), manual tasks with `legacy_action`, legacy keys only in code spans, and `external_event` waits that create marks blocked; GR-31 and GR-13 check it, and the proposal lists each legacy wait for the runner to confirm. Brief fields from working text are checked against it, or listed as not checked. Provisional run bundles may carry runner-supplied evidence, re-confirmed at promotion. New golden GA-adopt.
- Added (planning model build 4): change requests. The runner submits a request in their own words; `change_request.py` allocates its id under the lock as a pending entry in a new change-request log (outside `plan_hash`), checks that the plan and manifest haven't moved since the assessment, and assesses the impact: whether it changes the brief (shown first), what it serves, changed decisions, released phases whose basis changed, added traits, cost in one-day tasks (drafted, outline or unknown, with waits at 0 days), new dependencies and all four options (add, later phase, own epic, decline). Add is a revision; later, own epic and decline are plan-level sets, so a decline leaves pending approvals valid. Similar declined requests are shown. The log is scanned for secrets and restricted values. Revision write lists bind the log entry.
- Added (planning model build 3): approval sets. A record counts only toward the set it belongs to (same plan version and `proposal_hash`), and that grouping runs before any other per-record check, so a decline and a pending release at one version coexist and a broken record in one set can't fail another. Storing a new plan version voids every pending set at older versions. New plan-level sets (`scope: plan_level`, kinds `decline`, `own_epic`, `retire`, `later`) with their own quorum check (`check_hashes.py plan-level`), a plan-only write list, and an `integrity` validator profile. Every write-list entry carries `scope`. Plan-level proposals render only from stored inputs: the plan of record, the write list and a new stored `proposal-context` file; create stops for a new proposal if the epic gained an open item since.
- Fixed: a reviewed proposal said "No independent review is recorded" whenever no check was skipped.
- Added (planning model build 2): tracker states and closes. Every task with a `waits_on` now gets the tracker's blocked state at create through a new `set_blocked` write, applied once and never reapplied after a person clears it (fixes finding 8). Items Groundwork closes go through a close procedure: the intent is recorded in the manifest first, then a `gw-closed:<reason>` label, then the tracker's close, so a crash at any point resumes correctly. Readback (`create_steps.py status`) adds the status `closed_not_done`, which is never edited and never satisfies a dependency; a close label counts only when the manifest recorded it, and a reopened Groundwork close is drift. Overlays must map `field_map.statuses`. New tracker procedure `read_scope` with a limit of at most 200 items, for assess. The GitHub tracker skill gains a VERIFY.md.
- Added (planning model, plan format 2.0): a brief (one field per core key and per pinned trait question, each with its source and status, restricted values stored only as a revision), project traits (`reference/traits.yaml`, ten generic traits that add brief questions, standard work and roles, combined by union, with declared conflicts settled by a decision) and an approach (options including reuse and a smaller or do-nothing option, rejections that cite the brief, decisions that may be deferred to a design task, and resources left unchanged). Tasks trace to the brief through `brief_refs` and `approach_refs`. `plan_hash` covers the brief, traits and approach; a new informational `basis_hash` lists what a phase relies on. New checks GR-29 to GR-34; GR-02, GR-04, GR-06 and GR-19 extended. Overlays gain per-role `executor_profiles`, org-only `x-` traits and roles, and `org_process`, shown in proposals. New task kinds (spike, measurement, reconciliation), waits (elapsed, external event) and visible results (document, decision record, measurement). G1, G3 and G6 move to format 2; G7 adds a pasted document with a planted directive; ten trait goldens (GT-*) cover every trait and the moves_data and removes_something conflict. Format-1 plans validate and hash unchanged.
- Added (D-55): Clarify always asks what already exists (code, pipelines, docs, consumers) or whether the work starts from scratch, recorded in `request.starting_point`. Discover examines each resource read-only, including documents the runner supplies. Tasks that change an existing resource carry `changes_existing` (why needed, what it could break, which test or UAT task checks it). New checks GR-27 (validator) and GR-28 (reviewer); the proposal lists what already exists and which tasks change it. Goldens assert the starting point and justified changes.
- Fixed: create for a later phase always failed after an earlier phase was created, because approval records from the earlier plan version were checked against the new version and reported as void. Only records for the current `plan_version` now count; older ones are reported as superseded. Every gate that applies to all phases must now reach its own quorum (before, any one gate was enough). An empty phase list no longer means "all drafted phases" in `validate_plan.py` and `render_proposal.py`, and `check_hashes.py approvals` refuses to verify no phases.
- Added (D-54): plan without a tracker connection. A provisional overlay (`templates/provisional-overlay.yaml`) or an unconnected tracker gives a `plan_only` run through Proposal, rendered as provisional with no write list, no draft epic and no approvals. `run_bundle.py import` promotes an evidence-free provisional run into an approved overlay and asks for a rerun from Discover. When the tracker is connected, Intake shows open epics from the new `find_epics` read so the runner can add to one instead of starting new.
- Added (D-53): each task carries `work_type` (`story` or `task`), which sets the tracker item type, and each phase is released as a tracker release container (a Jira fix version or a GitHub milestone) created by a new `ensure_release` write. Overlays map both under `tracker.field_map` (`work_types`, `phase_release`). The G7 generator now writes its expected plan instead of relying on a hand copy.
- Fixed: `groundwork-core.zip` was rejected by the Claude app because the overlay template's `SKILL.md` made two in one ZIP. The template is now `templates/overlay-skill/SKILL.template.md`; the release build, boundary lint and release tests all refuse a skill with more than one `SKILL.md`.
- First implementation of the approved Groundwork v1 spec (draft 0.3, approved 2026-11-14): core skill, contract 1.0, plan format 1.0, overlay format 1.0, GitHub system skill, GitHub Issues and Jira Cloud tracker skills, golden project G1.
